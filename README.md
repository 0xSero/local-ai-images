# local-ai-images

Container images the [local-ai registry](https://github.com/0xSero/local-ai-registry)
pins when an upstream image cannot run a recipe as published. One directory per
image, one Dockerfile each, built only by the `release-image` workflow so every
published digest carries BuildKit provenance, an SBOM, and a GitHub build
attestation:

    gh attestation verify oci://ghcr.io/0xsero/<image>@sha256:<digest> -o 0xSero

| Image | Base | Why it exists |
|---|---|---|
| `gateway` | `python:3.12-slim` by digest | the plugin's one endpoint: OpenAI chat passes through, Anthropic Messages and OpenAI Responses are translated to the engine's chat completions, streaming and tool calls included; enforces the share key when one is set. `python3 gateway/test.py` runs its tests against a fake engine. |
| `tabbyapi-exl3` | `ghcr.io/theroyallab/tabbyapi:cu13` by digest | adds `python3-dev` and `build-essential`; without Python headers Triton cannot JIT ExLlamaV3's gated-delta-net kernels, so Qwen3.5 and Qwen3.8 fail to load |
| `llamacpp-prism` | `nvidia/cuda:12.8.1-runtime-ubuntu24.04` by digest | Prism ML's llama.cpp fork, whose ternary kernels are the only ones that load `Ternary-Bonsai-2-27B`'s `PTQ1_0`/`PQ2_0` packings; stock llama.cpp rejects them as unknown types. Ships the release tarball verified against its published `sha256`, a shim entrypoint that serves both the recipe argv and the campaign's SSH bootstrap, and `openssh-server` so the bootstrap does not need to install it |
| `llamacpp-upstream` | `nvidia/cuda:12.8.1-runtime-ubuntu24.04` by digest | stock, unmodified `ggml-org/llama.cpp` (release `b11112`) for every standard-quant GGUF row, so the campaign runs the latest upstream llama.cpp rather than the `llamacpp-prism` fork (Prism is only for `Ternary-Bonsai-2-27B`'s ternary packings). Same base, apt set, `/opt/llama` layout, shim entrypoint, and `openssh-server` as `llamacpp-prism`; the CUDA 12.8 x64 tarball is verified against its published `sha256` |
| `sglang-exl3-flashnext` | `ghcr.io/0xsero/sglang-exl3` v0.7.0-ampere by digest | Qwen3.8-Flash-Next EXL3 (3.05bpw_h5_ng5, 85 GB) on one 24 GB RTX 3090: [trellis-serve](https://github.com/0xSero/trellis-serve) `flashnext-phase-d` at `b1e74af` (the 1e72b25 vision build plus the Phase D defaults: 5-bit QSA KV, expert-cache reserve 8.26 GB, 12k prefill chunks), kernels compiled AOT for sm_86 in the build. Routed experts live in pinned host RAM behind a GPU expert cache, the 32.6 GB n-gram table on NVMe behind an 8 GB RAM row cache, so the host needs RAM for the 45.8 GB expert store plus caches, and a local NVMe SSD; the registry recipe states the exact VRAM / RAM / disk numbers |
| `sglang-exl3-xpu-flashnext` | `lmsysorg/sglang:v0.5.20-xpu` by digest | the same model on one Intel Arc Pro B70: trellis-serve `ft-xpu-vision` at `72fd2d4` (the 13f7ac1 build plus image input), with its SYCL/ESIMD dense, MoE and NVMe row-store libraries built by `xpu/scripts/build_ext.sh`, `build_moe.sh` and `build_ngram_nvme.sh` inside the base, plus oneDNN 2026.0.0 and the FFmpeg 6 shared libraries torchcodec needs for video input. Same two tiers (USM host RAM experts, NVMe n-gram table) |
| `glm53-flash-offload` | `lmsysorg/sglang:v0.5.20` by digest | GLM-5.3-Flash EXL3 (3.05bpw, 125 GB) on one 24 GB RTX 3090 + host DDR4 with an OpenAI-compatible API: [glm53-flash-offload](https://github.com/0xSero/glm53-flash-offload) at a pinned commit over stock exllamav3 v1.5.1 built for sm_86. All routed experts in pinned host RAM, an elastic GPU expert cache, and an AVX2 CPU tier for cold decode misses (`GLM53_MODE=fast`, ~218 GiB host RAM; `exact` without the tier, ~111 GiB). Bakes the routing stats, tune cache, Triton cache/pins and pre-built extensions; the checkpoint is mounted at `/models` or downloaded there by revision |
| `dsv41-flash-offload` | `lazymio/vllm-backport:v0.13.0` by digest | DeepSeek-V4.1-Flash EXL3 (3.0bpw, Mia-AiLab) on one 24 GB RTX 3090 + host DDR4 + NVMe with an OpenAI-compatible API (deepseek_v41 tool calls + reasoning): [dsv41-flash-offload](https://github.com/0xSero/dsv41-flash-offload) at a pinned commit over vLLM 0.13 + Ampere V4.1 patches + vllm-exl3/exllamav3 built for sm_86 (the campaign's D005 runtime as one Dockerfile). Campaign run D118: staged-DMA prefill with FP16 GEMM for busy experts, AVX2 CPU tier for decode misses, elastic VRAM expert cache, Engram tables mmap'd from NVMe; ~200 GiB host RAM pinned. Runtime patches are applied at build time and checked against the measured runs' sha256 receipts; `prepare` downloads the pinned inputs and builds the overlay pack under `/models` |
| `deepseek-v4.1-flash-spark` | `vllm/vllm-openai:v0.30.0` by digest (**linux/arm64**) | DeepSeek-V4.1-Flash-Spark (DeepSeek-V4.1-Flash, EXL3 routed experts) with vLLM TP2 across two DGX Spark (GB10, sm_121) over RoCE: local-inference-lab vLLM r38 + b12x rebuilt for `12.1a`, upstream turboderp exllamav3 1.5.3, and this directory's EXL3 MoE method + prefill grouped GEMM. Weights come from the private HF repo `0xSero/DeepSeek-V4.1-Flash-Spark`. Built with `platform=linux/arm64`; the digest pinned today was pushed from a Spark host (unattested) until that CI build lands, see its README |

Recipes reference the digest the workflow prints, never a tag. To publish:
run the workflow with the image directory and a tag, take the digest from the
run summary, and pin it in the registry recipe together with a link to the run.
